## 1. Executive assessment

GeoProduct Engineer is a working, well-engineered toolkit, not a prompt collection. It has typed contracts, a checkpointing pipeline engine, polite provider clients, an SSRF-guarded fetcher, a 21-tool MCP server and an Agent Skill whose documentation is checked by tests against the real server. The quality bar is high: strict typing, 423 passing tests, pinned CI, and 67 recorded design decisions.

The audit found **no P0 issues**. It found **three P1 correctness defects**, each reproduced by a probe:

1. **Deduplication chains.** It merges records that are not duplicates of each other: five same-name places spread over 560 m became one record.
2. **Overpass partial answers are cached.** One "query timed out" answer blocks the same query for up to 7 days, and the engine's retries never reach the network.
3. **The MCP status and results hide reused stages.** After a run is resumed, reused stages are left out, so agents see incomplete results on the documented recovery path.

All three are small or medium fixes, and none needs an architectural change. The remaining findings are robustness hardening (P3) and product gaps: no GeoPackage or GeoParquet export, packages not yet on PyPI, and only 3 skill evaluation cases.

## 3. Strengths worth preserving

- **The checkpoint model.** A stage's fingerprint combines the stage name and version, its parameters and the hashes of its input outputs (`engine/runner.py` `run_stage`). The manifest is written last (`engine/store.py`), and reuse re-hashes the outputs (`outputs_intact`). The probe confirmed that a reused stage's output was byte-identical and was not fetched again.
- **Path confinement** (`workspace.py`):
  - `Workspace.path` refuses anchors, `..`, `:` and `\` on every platform.
  - `user_path` resolves links and checks the result against an allowlist.
  - Ids are checked by regex before use: `RUN_ID`, `DATASET_ID`, `RUN_OUTPUT_ID` and `SOURCE_ID`.
- **The SSRF-safe fetcher** (`fetch.py`):
  - the address is checked when the connection is made;
  - IPv4-mapped IPv6 addresses are unwrapped first;
  - environment proxies are ignored;
  - at most 5 redirects;
  - a content-type allowlist and a size cap;
  - `robots.txt` is respected.
- **Provider politeness**:
  - a per-process throttle;
  - an identifying User-Agent is required for the public endpoints;
  - Nominatim is capped at 100 geocodes per run;
  - `Retry-After` is honoured;
  - endpoint URLs may not contain credentials;
  - the `confirm` gate applies above 25 calls.
- **Overpass safety.** Queries are built from structured tags, never from raw QL. Literals are quoted, and each query carries a server-side timeout and a `limit+1` row to detect truncation. Partial "remark" answers are refused.
- **Honest matching and merging.** `geo/buildings.py` never attaches a record to a footprint only because it is the nearest. `resolve/dedupe.py` turns disagreements into `Conflict` entries instead of picking a winner.
- **Errors** carry stable codes and hints, and `GeoProductError.from_exception` never echoes exception arguments, which could hold secrets.
- **CI**:
  - actions pinned by SHA, with `persist-credentials: false`;
  - a matrix of 3 operating systems × 3 Python versions;
  - a smoke test of the installed wheels;
  - release tests check versions, links, README counts, pinned actions and the absence of private names.
- **Skill–server consistency tests** (`tests/skill`): every tool, parameter, stage name and error code in the docs must exist in the code.

## 4. Confirmed critical and high-priority findings

### GP-01 · P1 · Provider reliability — Overpass partial answers are cached and replayed

- **Where:**
  - `packages/geoproduct-core/src/geoproduct/providers/http.py`, `HttpClient._request`: `self._cache.put(...)` runs after `_parse`.
  - `providers/overpass.py`, `OverpassProvider._run`: the `remark` check runs after the cached call returns.
- **Evidence:** probe 1. The mock Overpass answers once with HTTP 200 and `remark: "runtime error: Query timed out…"`, then with a full answer.
  - Three `features()` calls all failed with `timeout`, yet only one network call was made.
  - The cache file holds the remark body.
  - The existing test `test_overpass_partial_answers_are_refused` makes only one call, so it cannot see this.
- **Why it matters:**
  - The public Overpass instances return this remark when they are busy.
  - `timeout` is retryable (`RETRYABLE_CODES`), so the engine retries, but every retry is answered from the cache.
  - The same query then fails for `GEOPRODUCT_CACHE_TTL_HOURS` (7 days by default) in every run and in every tool call.
- **Fix:** let the provider validate a response before it is cached, using either of these:
  - an `accept: Callable[[Any], bool]` argument on `get_json` and `post_json`;
  - or Overpass raising before the result is stored.

  Keep the existing behaviour for valid answers.
- **Effort:** S.
- **Risks:** low. The cache key and format are unchanged.
- **Acceptance:** with a mock that answers remark-then-full:
  - the second `features()` call succeeds, after 2 network calls;
  - no file under `cache/http/overpass` contains `runtime error`.

### GP-02 · P1 · Entity resolution — duplicate clusters chain through intermediaries

- **Where:** `packages/geoproduct-core/src/geoproduct/resolve/dedupe.py`, `resolve()`. It takes connected components (`_components`, union-find) over pairwise `duplicates` links and merges each whole component.
- **Evidence:** probe 4. Five records named "Sample Pharmacy" sit in a line, 140 m apart, with the default settings (`max_distance_m` 150, `name_threshold` 0.88).
  - Result: **1 record, 4 merges.**
  - The first and last records are **560 m** apart.
  - No test covers clusters larger than a pair that are not mutually duplicates.
- **Why it matters:**
  - Chains of shops, bank branches and clinics are common in dense cities.
  - Chaining silently collapses distinct places into one record and keeps a single geometry (`_rank`). It is a data-loss-grade correctness error for the product's core promise.
- **Fix:** merge only clusters that are consistent as a whole.
  - Process links from the highest score down.
  - Add a record to a cluster only if it satisfies the duplicate rule with *every* member, so the cluster's diameter stays within `max_distance_m`.
  - Records left out stay separate, or are linked as `ambiguous`, with reasons.
- **Effort:** M.
- **Risks:** this changes outputs for some inputs. Re-check the evaluation case `sample-town-hospitals-to-buildings`, which expects one specific merge, and `tests/test_examples.py`.
- **Acceptance:**
  - The five-in-a-row probe yields at least 3 records.
  - In every output cluster, the largest pairwise distance is at most `max_distance_m`.
  - Every member pair passes the duplicate rule.
  - All existing tests pass.
- **Related assumption (needs your decision):** two genuinely different same-name branches less than 150 m apart are still merged on name and nearness alone. The rule could require corroboration (a shared identifier or address) for name-only merges beyond a shorter distance.

### GP-03 · P1 · MCP results — reused (`skipped`) stages are left out of status and results

- **Where:** `packages/geoproduct-mcp/src/geoproduct_mcp/tools/pipelines.py`:
  - `get_pipeline_status` (line 268, `finished_outputs` and the "n of m done" count) and `get_pipeline_results` (line 294) both filter on `StageStatus.succeeded` only;
  - `run_geo_pipeline` (line 229) builds its `finished` set the same way.

  In contrast:
  - `engine/runner.py:338` marks a reused stage as `StageStatus.skipped`;
  - `cli.py:187` treats `succeeded` and `skipped` alike;
  - `store.py:147`'s own hint says "only succeeded or reused stages have output".
- **Evidence:** probe 2. The `buildings` stage fails with HTTP 400, then the run is resumed. After the resume the stages read `clinics: skipped`, `buildings`, `matched` and `export: succeeded`, and the run reads `succeeded`.
  - `finished_outputs` and the results list only `buildings`, `matched` and `export`.
  - The summary reads "succeeded: 3 of 4 stage(s) done".
  - `datasets.info('<run>/clinics')` works, so the data exists and is only hidden.
  - `test_a_failed_run_is_resumed_with_corrected_parameters` does not assert the outputs after the resume.
- **Why it matters:**
  - Resume is the documented recovery path, and agents read these two tools to learn what a run produced.
  - The estimate also counts reused stages again, which can ask for `confirm` when it is not needed.
- **Fix:** add one helper, `has_output(status) = status in {succeeded, skipped}`, and use it in all three places and in the count.
- **Effort:** S.
- **Risks:** none known.
- **Acceptance:** in the probe 2 scenario:
  - `finished_outputs` lists all 4 stages;
  - the results return 4 outputs;
  - the summary says "4 of 4".

## 5. Geospatial-specific findings

**Verified correct (by reading the code; tests cover most of it):**

- **Axis order is lon/lat throughout the contracts.** Overpass needs lat/lon, and the code supplies it:
  - `around:r,lat,lon`;
  - bbox as `(s,w,n,e)`;
  - `poly:"lat lon …"` (`overpass.area_filters`).

  The Nominatim `viewbox` is ordered `west,north,east,south`, and its `boundingbox` is read as `south,north,west,east`. Both are correct.
- **Distances use haversine, or a local equirectangular projection centred on the feature** (`geo/metric.py`). This is documented as accurate to well under 1% at city scale. `pyproj` was deferred by decision 20, and it is not installed and not imported. This is consistent.
- **Antimeridian:**
  - bboxes that cross it are split, both in `area_shape` and for Overpass;
  - longitudes are wrapped in `LocalProjection`.
- **Building matching** (`geo/buildings.py`):
  - containment uses `covers` (boundaries count);
  - the search radius follows the location's precision, capped by `max_distance_m`;
  - ambiguity margin;
  - `exact` requires name, address or identifier evidence.
- **Geometry problems become quality findings, not exceptions** (decision log). `record_shape` tolerates unparsable geometry.

**Findings:**

- **GP-02** (above): dedupe chaining.
- **GP-01** (above): Overpass partial answers cached.
- **GP-11 · P3 · edge case (hypothesis, untested):** `BuildingIndex.near` and the dedupe `STRtree` queries buffer a point in degrees, without wrapping at ±180°. Records within metres of the antimeridian miss candidates on the other side. This is rare for the product's city-scale use.
  - Fix: query a second, shifted box when `|lon| + reach > 180`. Effort S.
  - Acceptance: a point at 179.9999° matches a footprint at −179.9999°.
- **Missing (opportunity, not a defect) · GP-12 · P2:** only GeoJSON and CSV are exported (`stages/output.py`). There is no GeoPackage, GeoParquet or FlatGeobuf. Adding them needs a new dependency (for example `pyogrio`, or `pyarrow` for GeoParquet), which is your call.
  - Acceptance: the exports round-trip through GDAL or `pyogrio.read_dataframe` with an identical feature count, the same geometry hashes and the attribution metadata.

## 6. Agent Skill and MCP findings

**The skill meets the Agent Skills spec:**

- frontmatter fields `name`, `description`, `license`, `compatibility` and `metadata`;
- progressive disclosure through the workflow and reference files;
- references one level deep;
- scripts that use only the standard library.

All of this is enforced by `tests/skill` (22 tests, passed). No defect was found in the skill itself. Its weak spot is evaluation depth, covered in GP-13.

**MCP:**

- **GP-03** (above).
- **GP-05 · P3 · transport security (verified by reading the code, not exploited):**
  - `server.py` `_loopback` (line 830) accepts any loopback address, such as `--host 127.0.0.2`, and `main` (line 879) passes it to `server.run("streamable-http", …)` without `transport_security`.
  - The SDK enables DNS-rebinding protection automatically only for the literal hosts `127.0.0.1`, `localhost` and `::1` (`.venv/Lib/site-packages/mcp/server/lowlevel/server.py:752–756`).
  - Fix: pass explicit `TransportSecuritySettings` (allowed hosts and origins for the chosen host and port), or accept only those three hosts. Effort S.
  - Acceptance: with `--host 127.0.0.2`, a request carrying `Host: attacker.example` is refused.
- **GP-06 · P3 · idempotency:**
  - `run_geo_pipeline` with a spec calls `state.runner.create(new_spec)` (line 237) **before** the provider check (line 240) and the confirmation check (line 241).
  - Each unconfirmed or misconfigured call leaves a new orphan `pending` run. The error hint returns the `run_id`, so a careful agent reuses it, but a retrying one does not.
  - Fix: estimate and check first, then create; or reuse a pending run with the same `spec_sha256`. Effort S.
  - Acceptance: two unconfirmed calls with the same spec leave at most one pending run.
- **GP-07 · P3 · resource limits (risk, not load-tested):**
  - **Cancelled work keeps running.** `calls.call` uses `anyio.to_thread.run_sync(..., abandon_on_cancel=True)`. A cancelled tool call that is blocked in an Overpass request (up to `timeout_s + 30` = 120 s) keeps its worker thread. It can still commit a dataset if it finishes before its next `check()`.
  - **Thread exhaustion.** Repeated cancel-and-retry loops can use up anyio's default pool of 40 threads.
  - **Unbounded error bodies.** `HttpClient._status_error` calls `response.read()` on 4xx answers with no size cap; `max_bytes` applies only on the 200 path.
  - Fix: cap the error-body read (for example 64 KiB); check `job.cancel` before `DatasetStore.commit`. Effort S.
- **GP-04 · P3 · observability:**
  - `engine/store.py` `RunStore.events` calls `json.loads` on every line.
  - A torn last line (a process killed mid-append, or a full disk) raises `JSONDecodeError`, so the `geoproduct://runs/{run_id}` resource (`server.py:784`) fails.
  - Evidence: probe 3.
  - Fix: skip undecodable lines. Effort S.
  - Acceptance: with a partial line appended, the resource still returns the last valid events.
- **Opportunity · GP-14 · P2:**
  - `confirm: true` is set by the model itself (decision 43). It puts a person in the loop only if the agent asks one.
  - Where the client supports MCP elicitation, the server could ask the user directly, and fall back to `confirm` elsewhere.
  - No new tool is needed. The tool set itself is coherent, and no tool is redundant.

## 7. Pipeline findings

- **Fail half-way, then resume (probe 2): safe.** The first run failed at `buildings`. The resume:
  - reused `clinics` without fetching it again (1 features request in total);
  - kept its output hashes identical;
  - ran `buildings`, `matched` and `export`;
  - ended `succeeded`.

  Neither the data nor any stage was duplicated. A run killed in a separate process is covered by the existing `tests/e2e/test_recovery.py::test_a_run_killed_mid_stage_resumes_in_a_new_process`, which passed.
- **Reuse is visible only through the defects above.** GP-03 hides reused stages and GP-04 breaks the event log after a crash. The engine itself is sound.
- **Known limits, accepted in the decision log (no action):**
  - the run lock works only within one process (decision 26);
  - the throttle works only within one process (decision 41);
  - `Runner.cancel` on a run that another process is executing marks it cancelled directly, a consequence of decision 26.
- **GP-08 · P3 · disk growth:** expired response-cache entries are ignored by `ResponseCache.get` but never deleted, and there is no command to prune old runs or datasets.
  - Fix: a `geoproduct prune` CLI command that deletes expired cache entries and runs older than N days. Effort S–M.
- **GP-09 · P3 · memory:** `get_pipeline_results` (`pipelines.py:303`) loads every stage's full output to build a 5-item preview. With `Limits.max_records` = 100,000 per stage, one call can hold several full datasets in memory.
  - Fix: store the preview in the stage manifest at `finish`, or read the first N items as a stream. Effort S.
- **Reuse across domains:** stages take generic tags, areas and parameters, and the 4 example pipelines (`hospitals`, `transport`, `commercial-buildings`, `csv-enrich`) are built from the same stages. Nothing is tied to one example.

## 8. Testing and security findings

- **Tests:** 423 pass. They are meaningful (behavioural names, real assertions, and e2e tests against loopback stub servers with a dead proxy for everything else). The gaps line up with the defects found:
  - no repeated-call test for the cache (GP-01);
  - no clusters larger than a pair that are not mutually duplicates (GP-02);
  - no assertions on outputs after a resume (GP-03);
  - no torn log line (GP-04).
- **Symlink escape:** `test_workspace.py:62` was skipped on this machine (link creation not permitted). Containment through links is therefore **not verified here**; the Linux and macOS CI runners cover it.
- **GP-10 · P3 · SSRF hardening (environment-dependent):**
  - `fetch.is_public` relies on `ipaddress.is_global`. On Python 3.14.2 this returns `True` for NAT64 addresses such as `64:ff9b::7f00:1` and `64:ff9b::a00:1`, which embed `127.0.0.1` and `10.0.0.1` (checked here).
  - On a network with a NAT64 gateway, such an address can reach the gateway's private IPv4 range.
  - Fix: unwrap `64:ff9b::/96` (and `64:ff9b:1::/48`) to the embedded IPv4 address before the check. Effort S.
  - Acceptance: those addresses are refused.
- **Secrets and hygiene:**
  - `git grep` for key, token and password patterns: no matches.
  - `.env*` is ignored, except `.env.example`.
  - The private `prd.txt` is excluded through `.git/info/exclude`.
  - There are no private project or place names, which a release test also enforces.
- **Dependencies:** version ranges are bounded (for example `shapely>=2.2,<3`), `uv.lock` is committed, and CI runs `uv sync --locked`. No vulnerability scan was run (none is installed; not claimed).

### GP-16 · P1 · Entity resolution: organisation-level identifiers establish site duplicates

**Observation.** A shared identifier corroborates a merge on its own. A website, phone or email often identifies an organisation (a chain's brand site, a central booking line) rather than one physical site, so nearby branches merge (A, B, E). Phase A's all-pairs rule does not help, because every pair of branches shares the identifier. `organisation_id` linking only applies beyond `max_distance_m`.

**Evidence.**
- Probes A, B and E.
- In `resolve/dedupe.py`, `corroborated = bool(shared) or (similar and address is True)`.
- `providers/osm.py` reads `website`, `contact:website` and `url`; `phone` and `contact:phone`; `email` and `contact:email`; and `wikidata`. It does not read `brand:wikidata`, so `wikidata` stays a site identifier.

**Effect on existing behaviour.**
- The fixture's two Sample General Hospital records (poi-01 and poi-02, 11 m apart, no addresses) merge only through their shared website.
- Under a strict rule they would stay apart as possible duplicates. The hospitals example would then deliver 5 facilities instead of 4, and graders 01 and 02 of the hospitals evaluation would fail.
- The README's replay of that example, and the end-to-end test, would also change.
- All of this is avoided if those two fixture records gain a shared address or site identifier.

**Recommendation.**
- **Two kinds of identifier.** Split `id_keys` into site-level keys (default `wikidata`, plus register or facility codes the user names) and organisation-level keys (default `website`, `phone`, `email`). Keep accepting `id_keys` for compatibility.
- **What a shared identifier proves.**
  - A shared site-level identifier corroborates a duplicate.
  - A shared organisation-level identifier never corroborates one on its own. It adds a reason and raises the score, and it links the records as one organisation. A merge still needs a site-level identifier or an agreeing address.
- **Values the data itself shows are shared.** A contact value used by more than two records in the dataset, or by two records further apart than `max_distance_m`, counts as organisation-level for that dataset, whatever its key.
- **What contradicts.** Differing organisation-level identifiers no longer keep records apart, because one site can have a direct line and a central line (D). They are recorded as differences. Differing site-level identifiers and addresses still contradict.
- **Rejected:** telling a site URL from a brand URL by its path, which is too fragile.

**Decision needed.** May a shared organisation-level identifier plus a similar name still merge when the records are within a tight same-site distance, for example 25 m (about one building)?
- With that allowance, the fixture hospital and the common OpenStreetMap duplicate of one place mapped twice (as a point and as an area) keep merging.
- Without it, they become possible duplicates until an address or site identifier is found.

### GP-17 · P1 · Entity resolution: comparing phones by their last 8 digits makes false matches (introduced in Phase A)

**Observation.** Phase A compares phone numbers by their last 8 digits, so that the international and national forms of one number agree. Numbers that differ in country or area code but share their last 8 digits now count as "same phone" (C), and an extension makes one number look different (D). The audited code compared all digits, so case C did not merge before Phase A. `same_category` blocks case C only when both records have categories and the categories differ.

**Evidence.** Probes C and D, and the phone keys listed above.

**Recommendation.**
1. **No new dependency** (P1, S):
   - Move an extension (`ext`, `x`, `#` and what follows) out of the number before comparing.
   - Two numbers match only if all their digits are equal.
   - An international number and a national one (leading `0`) that may be the same number are **ambiguous**: they neither confirm nor contradict, and the pair is reported as a possible duplicate with the reason "phones may match". This covers the case where the national digits without the `0` equal the end of the international digits.
   - Numbers shorter than 7 digits, such as short codes and emergency numbers, are never used as evidence.
2. **Optional, needs approval** (P2 part, S–M): normalise to E.164 with the `phonenumbers` package (the Python port of Google's libphonenumber). It would use the record's `address.country_code`, or a default region for the dataset.
   - It is not installed today and would be a new dependency of `geoproduct-core`; confirm its licence and size before adding it.
   - Numbers it cannot parse, or finds invalid, stay ambiguous as in step 1.

### GP-18 · P2 · Data model: possible duplicates are free text

**Observation.** Phase A records a possible duplicate as a sentence in `limitations`. This has several consequences:
- Consumers must parse the "Possible duplicate of" prefix.
- The five-line cap hides record ids.
- The confidence score ignores the mark.
- CSV joins it into the `limitations` column.
- A reviewer's decision has nowhere to go, so the next run flags the same pair again.
- `validate.dataset` detects same-name pairs within 25 m on its own: the end-to-end run reports the same two pairs again as `duplicates` warnings.

**Recommendation.** Add an optional `relations` list to `Record`. It is an additive change, which decision 62 allows within v1. Each relation has:
- `kind`: `possible_duplicate`, and later `same_organisation`, which GP-16's organisation links could use;
- `record_id`, `score` (the pair score, 0 to 1), `reasons`, `evidence_ids` and `why_not_merged`;
- `review`: `status` (`unreviewed`, `confirmed_same` or `confirmed_distinct`), `note`, `decided_by` and `decided_at`.

The supporting work:
- regenerate `schemas/v1/record.schema.json`;
- export relations to GeoJSON as they are, and to CSV as a `possible_duplicates` column of ids;
- let deduplication accept recorded review decisions: confirmed-distinct pairs are not flagged again, and confirmed-same pairs merge with the decision as evidence;
- have `validate.dataset` report unreviewed relations instead of detecting them again;
- add a confidence reason for unreviewed possible duplicates;
- during v1, keep a short `limitations` line generated from each relation, for readers of older outputs.

Effort M–L. It touches the contract, the exports, validation and confidence. If it adds an MCP tool for review decisions, the README's tool count changes.

### Behaviour changes to note

- **A shared website, phone or email no longer merges anything by default.** A dataset whose websites really are per site can say so with `site_keys: [website]`. A register or facility code should be named in `site_keys`.
- **Existing specs that use `id_keys: [website]` or `[phone]` now link instead of merge,** because those keys count as organisation-level.
- **Differing organisation-level identifiers still block a merge.** The follow-up recommendation proposed that they should not. A2 keeps them as "material conflicting evidence", the conservative reading of the approval. One site with a direct line and a central line, plus a shared `wikidata`, therefore stays apart as a possible duplicate. An unclear phone pair blocks nothing.
- **Not implemented from the recommendation:** treating a value shared by more than two records as organisation-level. Only the distance rule demotes site values. With `wikidata` as the only default site key, the count rule would matter only for keys the user names.
- The possible-duplicate reasons are more specific, for example "not merged because they share only organisation-level details (website), which do not identify a site".

### Remaining limitations

- **Possible duplicates are still text** (GP-18). The confidence score does not read them: the two unmerged hospital records are each `high` (0.75), resolved, with no confidence reason about the possible duplicate. This was already true in Phase A, and the evaluation's run agent noticed it.
- **Several numbers in one phone field** (for example separated by `;`) are compared as one long number.
- **A brand identifier in `wikidata`.** OpenStreetMap puts brands in `brand:wikidata`, which the provider does not read. Data that puts a brand's QID in `wikidata` can still merge branches that are close together; only far-apart branches are caught.
- **Provider feature ids are not site keys.** A place mapped twice in OpenStreetMap (as a point and as an area) stays a possible duplicate unless an address or `wikidata` confirms it.
- **International prefixes such as `011`** are not recognised as international; such numbers are compared as national numbers. Without a numbering plan, unclear comparisons stay unclear.
- **The fixture's own description** calls poi-01 and poi-02 "a hospital mapped twice by different sources", but the data carries no site-level evidence for it. The toolkit cannot know what the fixture's author meant, so the example now shows a possible duplicate. The fixture was not changed.

### GP-18 proposal: possible-duplicate relations

Approved as a future additive change; not implemented. A proposal for review:

**Schema.** An optional `relations` list on `Record`, empty by default:

| Field | Type | Meaning |
|---|---|---|
| `kind` | `possible_duplicate` | The only kind in v1. Organisation membership stays in `organisation_id`, so one fact has one place. |
| `record_id` | Identifier | The other record |
| `score` | Fraction | The pair score from deduplication |
| `reasons` | list of text, at least one | As today: "same website", "name similarity 1.00", "11 m apart" |
| `held_by` | `code` and `detail` | Why it was not merged. Codes: `organisation_only`, `no_site_evidence`, `differing_identifier`, `differing_address`, `names_differ`, `too_far`, `left_out_of_group`. |
| `differences` | list of field names | Fields whose values differ between the two, such as `attributes.beds`. An unmerged pair has no `conflicts`, so this is the only place the disagreement shows. |
| `evidence_ids` | list of Identifier | The evidence behind the shared values |
| `review` | `status`, `note`, `decided_by`, `decided_at` | `unreviewed` by default; `confirmed_same` or `confirmed_distinct` after review |

Both records carry the relation, each naming the other. `schemas/v1/record.schema.json` is regenerated, and a v1 reader that ignores unknown fields is unaffected.

**Validation.**
- On each record: no relation to itself; at most one relation per other record; `decided_by` and `decided_at` required once the status is not `unreviewed`.
- `validate.dataset` gets a `relations` check:
  - a relation naming a record that is not in the dataset: warning (a filtered dataset can legitimately drop one side);
  - a relation present on one side only, or with different review statuses on the two sides: error;
  - each unreviewed possible duplicate: one warning per pair;
  - a `confirmed_same` pair still delivered as two records: warning.
- The `duplicates` check skips pairs that already have a relation, so a pair is reported once, not twice as in the end-to-end run today.

**Review workflow.**
- Decisions are data, so they are reproducible: a `reviews` parameter on `prepare.dedupe`, a list of `{records: [a, b], status, note, decided_by, decided_at}`, or a file of them. Decisions are part of the stage's fingerprint, so a changed decision reruns the stage.
- On a rerun:
  - `confirmed_distinct`: the pair is neither merged nor flagged again. If site-level evidence later says otherwise, the decision still holds and a stage note says it contradicts the evidence.
  - `confirmed_same`: the pair merges, with the decision as a merge reason. Their differences become `conflicts`, as in any merge.
  - A decision naming a record that no longer exists is reported in the stage notes.
- An MCP tool for recording decisions can come later (with GP-14 elicitation). It would change the README's tool count.

**Confidence.** An unreviewed possible duplicate lowers the consistency part of the score from 0.15 to 0.05 and adds the reason "possible duplicate of <id>, not reviewed". The level is capped at `medium` while any such relation is unreviewed. `confirmed_distinct` removes the penalty; `confirmed_same` leads to a merge. In the hospitals example, both hospital records would go from `high` (0.75) to `medium` (0.65), and the README replay would change again.

**CSV.** One `possible_duplicates` column: the other records' ids joined with `;` (ids cannot contain `;` or spaces), and a `possible_duplicates_review` column with the matching statuses. GeoJSON carries `relations` as they are. During v1 the short `limitations` line stays, generated from each relation, for readers of older outputs; the five-line cap applies only to that text, not to the relations.

**Effort.** M–L: the contract, dedupe, validation, confidence, both exports, the skill's matching rules, and new fixtures. One open question for review: whether to add a `same_organisation` kind later, or keep `organisation_id` as the only representation of organisation membership (this proposal assumes the latter).

### Behaviour changes to note

- **Checking the same spec twice returns the same `run_id`** while that run has not started. A caller who wanted two pending runs of one spec gets one; different parameters still make another run. A confirmed call made while a run of the same spec is executing records its own run, as before; only if two calls both look before either has started can the second be told "This run is already executing" instead.
- **A spec whose provider is not configured records no run.** Its error is unchanged, and it never carried a `run_id`.
- **HTTP requests must name the address served.** A client that reaches `127.0.0.2` through a hosts-file alias is refused; it must use the address. For `127.0.0.1`, `localhost` and `::1` the allowed names are the SDK's own set, with the bare names on port 80 added.
- **`events.jsonl` is written with `\n` line ends on every platform**, where Windows wrote `\r\n`. Readers that split lines are unaffected.
- **`get_pipeline_results` previews are unchanged** in content, as the tool-level test checks.

### Remaining limitations

- **Cancelled threads still run** (GP-24). Python cannot stop a thread, so a cancelled call's worker runs until its blocking work returns, an Overpass request for up to 120 s. Nothing is stored, but cancel-and-retry loops can still use up anyio's 40 worker threads. An export with `copy_to` writes its copy during the stage, so a call cancelled after that keeps the copy outside the workspace, though not the dataset. Not load-tested.
- **Pending-run reuse looks at the 20 newest runs.** An orphan older than that is not found, and a new run is recorded, as before. Orphans left by earlier versions are not removed (that is GP-08's job).
- **Torn lines are skipped silently.** The run's state is in `run.json`; the log does not report how many lines it skipped.
- **Streaming previews rely on the engine's compact GeoJSON layout.** A file written another way is still read, but whole.
- **NAT64 was checked at the address level, not on a NAT64 network.** No gateway is available here; the test covers the decision `fetch_source_data` makes for each resolved address.
- **Not covered:** the other items of §12 stand, including a clean-machine install and MCP clients other than the SDK's.
